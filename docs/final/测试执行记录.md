### 存档为什么能进单测

`Preferences` 需要 `UIAbilityContext`，hypium 里没有。所以拆成两层：

- `store/SaveCodec.ets`：纯函数 `encodeState` / `decodeState`，无 Context、无 IO —— T9/T12 测的是这一层；
- `store/SaveRepository.ets`：只做 `getPreferences / put / flush / get`，异常一律转成返回值。

这意味着"损坏降级"的每条分支都是被真实代码路径测过的，不是文档里写写。

## 一个真实死路与修复（可直接写进报告）

**现象**：先选「直接问值班保安」，再选「按保安口述记下时间」，进入监控回放时两个选项同时置灰，都提示"还缺线索「B1 门禁记录」"，流程彻底卡住，只能杀进程重来。

**根因有两层**：

1. `n_b1_tape` 节点把 `requireClues: [CLUE_DOOR]` 当作**进入门槛**，而"问保安"路线拿不到这条线索；
2. 「要求调门禁后台记录」又要求 `CLUE_LOG`，而 `CLUE_LOG` 只在另一个选项里给——两个"省时间"的选择叠在一起，就再也没有补救机会。

**修复**：

- 监控回放节点不再设门槛，证据要求下放到选项：没有门禁记录仍能进来，只是取不走完整画面（`ch_tape_full` 需要 `CLUE_DOOR` + `DEDUCE_GAP`）；
- 新增「让保安陪你回门厅翻那沓记录」，仅在走过 `guard_talk` 后出现，40 分钟补回 `CLUE_LOG + CLUE_DOOR`，总耗时与直达路线持平（10+40 = 30+20），"省时间"不再是单向陷阱；
- 「按保安口述」的提示改为直接说明代价："省下时间，但门禁记录这条证据链会断"。

**同批修掉一处隐性断链**：看台「先陪他坐一会儿」原本只给 `witness_calm`，而开 37 号柜要 `witness_flip`，等于耐心路线永远拿不到纸条、永远凑不齐 5 条线索。现已同时给 `witness_flip`。

**另补一个缺失入口**：`ch_tape_full` 要求推论 `d_gap`，但场景页此前没有任何做推理的地方，导致完整回放永远灰着、A 结局不可达。现已加入线索板（两两组合验证），并在现场页常驻入口。

## 一次真实缺陷与修复（可写进报告）

首次执行结果为 **8 通过 / 1 失败**：

```
Error in T4_clue_grant_is_idempotent, expect 0 equals 1
```

原因：T4 用全新状态直接跳到 `n_b1_shelf` 领取线索，而该选项的目标节点 `n_b1_tape`
要求前置线索 `CLUE_DOOR`（门禁记录），于是被引擎的 `canEnter` 守卫拦下，
`applyChoice` 返回 `ok=false`，线索数仍为 0。

判定：**引擎行为正确，测试用例的准备步骤缺失**。修复方式是把用例的前提补齐
（预置 `CLUE_DOOR`），并新增 `GameState.countClue()` 直接断言"同一条线索只被记录一次"，
让该用例只验证幂等性这一件事。修复后 9/9 通过。

这条"先失败、再定位、再修复"的记录比一次全绿更能说明测试是真的在跑。
