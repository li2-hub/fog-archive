## 1. 实验目的

1. 用 ArkTS + ArkUI 声明式开发完成一个**有完整业务闭环**的 HarmonyOS 应用，而不是若干个互不相干的 API 练习：从入口、玩法循环、状态推进、存档恢复，一直到结局复盘。
2. 掌握**单向数据流**的组织方式：把"业务规则"和"界面渲染"彻底分开，规则写成纯函数，界面只负责展示与派发意图。
3. 掌握 **Preferences 持久化**与"损坏存档降级"这类真实工程问题的处理方式，并让这部分逻辑也能被自动化测试覆盖。
4. 掌握 `@ohos/hypium` 单元测试的写法与**在设备上真实执行**的流程（编译 → 安装 → `aa test` → 读取报告），并养成"用例失败先判断是代码错还是用例错"的习惯。
5. 掌握 ArkUI 过渡动画（`animateTo`、`transition`）在状态变化场景下的用法，让"选择真的改变了状态"这件事看得见。

## 4. 实验原理

### 4.1 分层与依赖方向

```
pages / view  →  store  →  engine  →  model
（渲染与派发）  （持久化）  （纯函数规则）  （类型与数据表）
```

依赖严格单向：`model` 不认识任何上层，`engine` 不认识 UI 与 `Context`。这样做的直接收益是——**规则可以脱离设备跑测试**。15 条用例里只有 2 条（T9/T12）与存档编解码有关，其余 13 条都只 import 引擎与数据表，一条 `new GameState()` 就能构造被测对象。

### 4.2 状态容器与"不原地修改"

`GameState` 是唯一可变真相，但它从不被原地修改。引擎的每个入口（`applyChoice`、`tryDeduce`）都是：读入参 → `clone()` → 在副本上改 → 返回 `ApplyResult{ ok, reason, state }`。

```ts
// engine/GameEngine.ets（节选）
const next: GameState = state.clone();
next.timeLeft = state.timeLeft - choice.cost;
next.turn = state.turn + 1;
// 线索幂等：已在袋里的不再 push
for (const id of choice.grantClues) {
  if (!next.hasClue(id)) {
    next.collectedClues.push(id);
  }
}
next.currentNodeId = target.id;
next.stage = target.stage;
```

失败不抛异常，而是携带 `reason` 返回。界面拿到 `ok === false` 就弹 toast，拿到 `ok === true` 就整体替换 `@State`。好处是"所有失败路径"都是可枚举、可测试的数据，而不是散落在各处的 `try/catch`。

### 4.3 一次点击的完整链路

```
用户点选项
  → FogScene.apply(choice)
    → applyChoiceById(state, choiceId, now)      // 引擎：守卫 → clone → 扣时间 → 记线索 → 换节点
      → isChoiceAvailable(choice, state)         // 线索 / 推论 / 标记 / 时间四类校验
      → canEnter(target, state)                  // 目标节点级守卫
      → resolveEnding(...)                       // 若该选项是最终判断，直接定结局
    → animateTo { this.state = result.state }    // UI：HUD 与进度条平滑过渡
    → applyEndingView(result.state)              // 若已结局，切到封存卡视图
    → saveState(context, state)                  // Preferences 落盘
    → 若本次有新线索 → showFlash(names)          // 浮层提示，2 秒后淡出
```

### 4.4 剧情数据表与"守卫的粒度"

节点与选项都是纯数据，条件写在数据里而不是写在 `if` 里：

```ts
{
  id: 'ch_tape_full', label: '把缺口前后对齐看一遍',
  nextNodeId: 'n_lab_corridor', cost: 25,
  requireClues: [CLUE_DOOR], requireDeductions: [DEDUCE_GAP],
  requireFlags: [], grantClues: [CLUE_TAPE], setFlags: [],
  finalChoice: FinalChoice.NONE
}
```

这里有一条**踩坑后确立的设计约定**（第 7 节详述）：**线性剧情节点不设 `requireClues` 硬门槛，门槛一律下放到选项，且每个节点必须留一条无前置的保底选项。** 否则一旦某条路线拿不到那条线索，玩家就会被永久锁死在一个节点上，既进不去也退不出。

### 4.5 存档：为什么拆成两层

Preferences 需要 `UIAbilityContext`，而 hypium 单测里没有 Context。于是把"编码"和"IO"拆开：

| 层 | 文件 | 职责 | 可否单测 |
|---|---|---|---|
| 编解码 | `store/SaveCodec.ets` | 纯函数 `encodeState` / `decodeState`，逐字段校验、未知 id 过滤、重复去重、时间夹紧到 `[0, 480]` | 可以（T9/T12） |
| IO | `store/SaveRepository.ets` | `getPreferences / put / flush / delete`，异常一律转成返回值，不向上抛 | 需要设备 |

损坏降级的判定条件：空串、JSON 截断、`version` 不认识、`currentNodeId` 指向已删除节点、结局节点缺 `endingId`。命中任意一条就丢弃旧档并开新档，同时 toast 说明原因，绝不把半损坏状态喂给引擎。

### 4.6 结局复盘：把"为什么是这个结局"算出来

结局页不写死文案，而是在 `engine/Review.ets` 里用同一个 `resolveEnding` 的条件口径算出四条条件：

```ts
stats.items.push(new ReviewItem('在最终判断里提交完整证据链', submitted, ...));
stats.items.push(new ReviewItem(`推论「${deductionName(DEDUCE_GAP)}」成立`, state.hasDeduction(DEDUCE_GAP), ...));
stats.items.push(new ReviewItem(`推论「${deductionName(DEDUCE_WHO)}」成立`, state.hasDeduction(DEDUCE_WHO), ...));
stats.items.push(new ReviewItem(`归档线索不少于 ${MIN_CLUES_FOR_TRUTH} 条`, enough, `已归档 ${n} / ${total} 条`));
```

这样"判定结局"和"解释结局"用的是同一套常量（`MIN_CLUES_FOR_TRUTH`），不会出现"判定说缺 5 条、复盘说缺 4 条"的文案打架。

### 4.7 动画原理

| 场景 | 实现 | 时长 |
|---|---|---|
| 页面进入 | `aboutToAppear` 里 `animateTo` 把 `appear` 从 0 到 1，驱动根容器 `opacity + translate` | 320ms |
| 线索入袋 | 浮层 `opacity + translate({y})`，`setTimeout` 2s 后反向 | 200 / 320ms |
| 推论成立 | 结论卡带 `transition(OPACITY + translate)` 插入 | 260ms |
| 推理失败 | 三段 `animateTo` 依次 `x = -6 → 6 → 0`，作用在线索板整块面板上 | 60/60/90ms |
| HUD 进度 | 状态替换包在 `animateTo` 内，`Progress` 的 `value` 随之插值 | 280ms |
| 结局页逐条浮现 | 递归 `setTimeout` 每 90ms 让 `reveal` 加一，条目按索引取 `opacity/translate` | 90ms × 10 |

结局页的逐条浮现特意**递归**而不是在 `for` 循环里挂定时器：循环变量会被闭包共享，十个定时器最终都会读到同一个终值，导致"一次性全亮"。

### 5.3 关键代码：选项可用性与拒绝原因

```ts
export function isChoiceAvailable(choice: ChoiceDef, state: GameState): ChoiceAvailability {
  if (state.endingId !== EndingId.NONE) {
    return new ChoiceAvailability(false, '调查已经结束');
  }
  const missing: string[] = [];
  for (const id of choice.requireClues) {
    if (!state.hasClue(id)) missing.push(`线索「${clueName(id)}」`);
  }
  for (const id of choice.requireDeductions) {
    if (!state.hasDeduction(id)) missing.push(`推论「${deductionName(id)}」`);
  }
  for (const id of choice.requireFlags) {
    if (!state.hasFlag(id)) missing.push('前置对话没有完成');
  }
  if (missing.length > 0) {
    return new ChoiceAvailability(false, `还缺 ${missing.join('、')}`);
  }
  if (choice.cost > state.timeLeft) {
    return new ChoiceAvailability(false, `时间不够，还差 ${choice.cost - state.timeLeft} 分钟`);
  }
  return new ChoiceAvailability(true, '');
}
```

界面**不隐藏**不可用的选项，只把它置灰并显示 `reason`：

```ts
Text(this.available(choice).ok ? choice.hint : this.available(choice).reason)
  .fontSize(11)
  .fontColor(this.available(choice).ok ? C_MUTED : C_WARN)
```

这是有意为之：让玩家看到"这个选择存在，只是我还不够格"，比凭空少一个按钮更能传达"状态影响了选择"。

### 5.4 关键代码：推理验证

```ts
export function tryDeduce(state: GameState, a: string, b: string, now: number): DeduceResult {
  // 顺序无关：两种排列都试一遍
  for (const def of DEDUCTIONS) {
    const matched: boolean =
      (def.clueA === a && def.clueB === b) || (def.clueA === b && def.clueB === a);
    if (!matched) continue;
    if (state.hasDeduction(def.id)) {
      return new DeduceResult(false, def.id, '', '这条推论已经成立过了', state);
    }
    const next: GameState = state.clone();
    next.deductions.push(def.id);
    next.updatedAt = now;
    return new DeduceResult(true, def.id, def.conclusion, '', next);
  }
  return new DeduceResult(false, '', '', '这两条线索放在一起，还推不出结论', state);
}
```

### 5.5 关键代码：结局判定与复盘同源

```ts
export const MIN_CLUES_FOR_TRUTH: number = 5;

export function resolveEnding(state: GameState, finalChoice: FinalChoice): EndingId {
  if (finalChoice !== FinalChoice.SUBMIT) return EndingId.SCAPEGOAT;
  if (!state.hasDeduction(DEDUCE_GAP) || !state.hasDeduction(DEDUCE_WHO)) return EndingId.SCAPEGOAT;
  if (state.collectedClues.length < MIN_CLUES_FOR_TRUTH) return EndingId.SCAPEGOAT;
  return EndingId.TRUTH;
}
```

结局页不是"另写一套判断"，而是把同样的条件逐条列出来并附上人话说明，所以 B 结局的复盘能明确指出"你选择了只交人情 / 这条推论没有验证过 / 已归档 3 / 6 条"（截图 19）。

## 7. 调试记录（真实问题与修复）

### 7.1 用例失败，但错的是用例不是引擎（T4）

首次执行 8 通过 / 1 失败：`T4_clue_grant_is_idempotent, expect 0 equals 1`。定位后发现 T4 用全新状态直接跳到 `n_b1_shelf` 领线索，而该选项的目标节点当时要求 `CLUE_DOOR`，被 `canEnter` 拦下，线索数仍为 0。

判定：**引擎行为正确，用例准备缺失**。修复是把用例前提补齐，并新增 `countClue()` 让断言只针对"幂等"这一件事。这条记录比一次全绿更能说明测试是真跑的。

### 7.2 真实死路：走"问保安"路线会被永久锁死

**现象**：选「直接问值班保安」→「按保安口述记下时间」→ 进入监控回放，两个选项同时置灰，都提示"还缺线索「B1 门禁记录」"，流程彻底卡死，只能杀进程重来。

**根因两层**：

1. `n_b1_tape` 把 `requireClues: [CLUE_DOOR]` 当作**进入门槛**，而问保安路线拿不到这条线索；
2. 「要求调门禁后台记录」又要求 `CLUE_LOG`，而它只在另一个选项里给——两个"省时间"的选择叠在一起，再无补救机会。

**修复**：节点门槛移除，证据要求下放到选项；新增「让保安陪你回门厅翻那沓记录」（仅走过 `guard_talk` 后出现，40 分钟补回 `CLUE_LOG + CLUE_DOOR`，与直达路线 10+40 = 30+20 总耗时持平）；「按保安口述」的提示改为明示代价。并补 T10/T11 两条回归用例，把"这条路能走通"钉死。

### 7.3 两个隐性断链：A 结局其实不可达

修复 7.2 时又发现两处：

- `ch_tape_full` 要求推论 `d_gap`，但场景页**根本没有做推理的入口**，导致完整回放永远灰着、A 结局不可达 → 新增线索板（两两组合验证），并在现场页常驻入口。
- 看台「先陪他坐一会儿」只给 `witness_calm`，而开 37 号柜要 `witness_flip`，等于"耐心"路线永远拿不到纸条、永远凑不齐 5 条线索 → 该选项同时给 `witness_flip`。

### 7.4 新功能的两个小坑

| 现象 | 原因 | 修复 |
|---|---|---|
| 编译报 `Expected 2 arguments, but got 1` | `startReveal` 改成"索引 + 总数"的递归签名后，调用处只传了总数 | 改为 `startReveal(0, total)` |
| 现场页残留一个孤立的 ✓ | 线索浮层始终占位（避免正文跳动），但 `✓` 图标不受 `opacity` 控制，空文案时仍可见 | 给浮层加 `visibility(flashText === '' ? Hidden : Visible)`，占位保留、内容隐藏 |

### 7.5 环境类坑（与代码无关但耗时间）

| 现象 | 处理 |
|---|---|
| 命令行构建报找不到 SDK | 必须先 `export DEVECO_SDK_HOME="F:/DevEco Studio/sdk"`，IDE 内会自动注入 |
| 模拟器报 `Invalid parameters, api type is: 5` | `Emulator.exe -path` 要传实例的**父目录**（`F:/HUAWEImoniqi`），`-imageRoot` 指 `.../sdk` |
| `hdc file recv` / `install` 路径被改写 | Git Bash 下必须 `export MSYS_NO_PATHCONV=1`，否则 `/data/local/tmp/x` 会被拼成 Windows 路径 |
| 点按钮点不中 | 用 `uitest dumpLayout` 取真实 `bounds` 再点，不要靠截图目测（曾差 11px 点空） |
| `Scroll` 内容短于视口时正文浮在中间 | `Scroll` 要显式 `.align(Alignment.Top)` |

## 8. AI 辅助说明

本次作业在**明确的人工主导**下使用了 AI 编码助手，过程如实记录如下。

**AI 参与的环节**

1. 需求梳理与计划书初稿（节点表、线索表、结局条件表的结构）。
2. 引擎与数据表的初版代码、单元测试骨架。
3. 页面骨架与视觉风格（深色档案 + 琥珀强调）的初版。
4. 文档排版与术语统一。

**人工主导的环节**

1. **设计决策**：选题、12 节点剧情骨架、双结局条件口径、"门槛下放到选项"这一约定，均由本人拍定后写入计划，再让 AI 按此实现。
2. **真机验证**：所有"能不能走通"的判断都来自模拟器实跑（`hdc` 安装 → `uitest` 点击 → 截图），不采信"代码看起来对"。
3. **缺陷判定**：7.1 的 T4 失败，是先判断"引擎对、用例错"才动手改；7.2 的死路是本人实机走出来的，AI 只负责按结论改数据表。
4. **验收口径**：测试必须真跑出 `Tests run: 15, Failure: 0`，截图与日志归档进仓库，不接受"应该能过"。

**AI 产出的修改与纠正记录**

| 轮次 | AI 初版的问题 | 人工如何发现与纠正 |
|---|---|---|
| 剧情表 | `n_b1_tape` 用节点门槛表达"需要门禁记录" | 实机走死路发现 → 改为选项级门槛并补保底选项 |
| 剧情表 | 缺少推理入口，`d_gap` 无法产生 | 推演 A 结局可达性时发现 → 增加线索板 |
| 剧情表 | 耐心路线只给 `witness_calm` | 同上 → 补 `witness_flip` |
| 测试 | T4 缺少前置准备 | 实跑失败后定位 → 补前提 |
| 页面 | `Scroll` 竖直居中、状态栏白条、`Button` 不支持 `letterSpacing` | 截图与实机检查发现 → 逐项修正 |
| 结局页 | 逐条浮现用循环挂定时器会一次性全亮 | 自查闭包语义 → 改递归 |
| 结局页 | 线索浮层空文案时残留 ✓ | 实机截图发现 → 加 `visibility` |

**结论**：AI 显著加快了"写出来"的速度，但**能不能跑通、走不走得通、文案与条件是否一致**这三件事必须由人用设备验证。本项目 4 个真实缺陷（死路、A 结局不可达、耐心路线断链、浮层残留）全部是在真机验证阶段暴露的，这也是本报告最有价值的部分。

## 9. 实验总结

**做对的地方**

1. 先定数据表、再写引擎、最后写界面。12 个节点写成表格后，"条件链是否闭合"这类问题在写代码前就能推演一遍；虽然仍漏了两处，但都能被定位到具体某一行数据，改起来是改数据而不是改逻辑。
2. 引擎纯函数化的收益远超预期：15 条用例里 13 条不需要设备能力，改一行数据表跑一次 `aa test` 就知道有没有破坏别的路线。
3. 存档拆两层是被"要有异常测试"逼出来的设计，结果反而让"损坏降级"这种最容易敷衍的部分变成了真正被覆盖的代码路径。
4. 拒绝类反馈给"原因"而不只是"不可用"：置灰选项写明缺什么、复盘页写明差哪几项，玩家的困惑少了，作品的可信度也高了。

**不足**

1. 界面组件仍集中在一个 835 行的页面文件里，`view/` 目录空着。后续如果再加场景，应该按"场景是否复用同一套渲染"来抽组件。
2. 只做了手机竖屏适配，平板 / 2in1 的布局没有专门验证。
3. 时间系统只有"扣减"，没有让时间紧张度影响结局评级；480 分钟对熟悉路线的人来说偏宽松。
4. 未做性能数据采集（首屏耗时、帧率），录屏也未录制，报告里只能给分镜脚本。
5. 剧情文本量偏小（每节点一段），分支的"文本差异"更多体现在选项与结局上，而不是同一节点的多套叙述。

**后续改进**

1. 按 `reduceMotion` 增加"减弱动画"开关，照顾眩晕敏感用户。
2. 时间改为分段压力（例如剩余 < 90 分钟时插入额外事件），让"省时间"的路线付出叙事代价而不只是少一条线索。
3. 增加"档案柜"：把历史结局存档保留下来，做成多周目收集。

**收获**

这次作业真正的难点不是某个 API，而是**把"状态"当成唯一真相来设计**：一旦承认所有展示都是状态的函数，很多问题（HUD 不同步、返回丢状态、杀进程丢进度、结局页与判定不一致）就变成了"状态有没有被正确落盘/派生"的工程问题，而不是散落各处的 UI bug。ArkUI 的声明式模型与这套思路天然契合，`@State` + 单向数据流的组合在小规模业务里足够清晰，不必引入更重的状态管理方案。
